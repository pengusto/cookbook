# Handoff to a destination

Prepare the smallest useful handoff for the named host, project, chat or next
agent. Recover the destination from context; ask only when ambiguity changes
where work would happen. Preserve the current finish line and existing limits.

Include the outcome and accepted decisions, intended host and project root,
relevant repository/base/head or artifact, completed checks with their limits,
open work and first discriminating check at the destination. Distinguish
current authorization from historical instructions. Preserve explicit limits
such as no deployment, no new scans or no change on the source host. Describe
the retained recovery path when an installation or migration is involved.

Reference existing specs, commits and handoffs instead of copying their
contents. Keep credentials and unrelated private information out. A small
handoff can be a copyable prompt; create a durable file only when requested
or useful for the next work block, using the project's established location.

A prepared prompt is not a completed transfer. When the user also explicitly
authorizes sending to a named chat or moving work to a named host, use the
supported host action and verify its result. Verify destination host, project
membership and execution directory as separate facts. If runtime context is
not observable, mark it unverified and give the first destination check.
Do not create a replacement chat, archive the source or move files as an
implicit substitute. State a specific unavailable action without claiming it
succeeded. Independent authorized preparation can finish while a transfer gate
remains open.
